# 大数据量迁移基准（v1.4.2）

> 问题：**只打一个 jar 包部署，会影响迁移速度或大数据量迁移吗？**
> 结论：**打包方式本身不影响**。Spring Boot 单 jar 只是把 Web 与迁移引擎放进同一个 JVM 进程，速度与容量取决于「取数方式、批量写入方式、内存/GC、网络」。本页是在 4C8G 测试机上的真实基准，以及据此做的两项关键优化。

## 1. 测试环境

| 项 | 配置 |
|---|---|
| 机器 | 4 vCPU / 7.7GB，局域网测试机（Ubuntu 24.04） |
| 应用 | 单 jar（29MB fat jar），`-Xms1g -Xmx2g`，G1GC |
| 数据库 | 本地 MySQL 8.0.46，表 100 万～500 万行 |
| FTP | 本机 vsftpd（真实 FTP 传输，非 mock） |
| 远程数据源 | 本机 MySQL，直连（跨库迁移链路与跨网络一致，仅少代理一跳） |

## 2. 优化前后的关键差异

| 问题 | 优化前 | 优化后 |
|---|---|---|
| 远程/本地取数 | MySQL 驱动默认**把整个结果集读进内存** | 远程连接启用 `useCursorFetch=true&useServerPrepStmts=true`，按 fetchSize 流式读；本地导出用 `Integer.MIN_VALUE` 流式逐行 |
| 目标写入 | 逐行 `addBatch`（500 行/批，但每条 INSERT 单独发送） | **多行 INSERT**：一条语句写 500～2000 行（跨库 2000、文件导入 500） |
| 连接参数 | 无批量重写 | 远程 MySQL URL 追加 `rewriteBatchedStatements=true` |

## 3. 实测结果（1 万→500 万行）

| 场景 | 数据量 | 耗时 | 速率 | 峰值内存(RSS) |
|---|---|---|---|---|
| 同库 `INSERT…SELECT` | 100 万 | 5.3s | **18.9 万行/s** | 340 MB |
| 同库 `INSERT…SELECT` | 200 万 | 10.9s | 18.4 万行/s | 388 MB |
| 同库 `INSERT…SELECT` | **500 万** | 26.0s | **19.2 万行/s** | 375 MB |
| 跨库迁移（远程读→本地写） | 100 万 | 12.4s | 8.1 万行/s | 910 MB |
| 跨库迁移 | 200 万 | 23.1s | 8.7 万行/s | 900 MB |
| 跨库迁移 | **500 万** | 56.4s | **8.9 万行/s** | **878 MB（持平）** |
| FTP 导出 CSV | 100 万 | 1.9s | — | 912 MB |
| FTP 导出 CSV | 500 万 | 7.1s（218MB 文件） | — | 879 MB |
| FTP 导入 CSV | 100 万 | 10.4s | 9.6 万行/s | 922 MB |
| FTP 导入 CSV | **500 万** | 49.5s | **10.1 万行/s** | **883 MB（持平）** |

**关键点：数据量从 100 万涨到 500 万，内存基本不变（≈880MB）**，说明取数是流式的，不会随表大小线性吃内存。优化前仅 100 万行跨库迁移峰值就到 **1.33GB**（整表缓冲），500 万行必然 OOM；优化后 500 万行仍稳在 880MB。

## 4. 容量参考（单 jar，4C8G，-Xmx2g）

| 数据量 | 建议方式 | 预计耗时 |
|---|---|---|
| ≤ 100 万行 | 全量迁移 / FTP 均可，默认参数 | 同库 <10s、跨库 ~15s、FTP 约 15s |
| 100 万 ～ 1000 万行 | 全量或增量分批（batchSize 2000～5000） | 10 分钟以内 |
| 1000 万 ～ 1 亿行 | **增量模式 + 水位分批**，避开业务高峰 | 小时级 |
| > 1 亿行 | 增量 + 分批 + 目标表关闭二级索引后重建 / 分区表 | 按批滚动，建议夜间窗口 |

> FTP 文件大小参考：5,000,000 行 CSV ≈ 218MB；开 gzip 一般压到 30% 左右（任务里可勾选）。

## 5. 调优建议

- **JVM**：默认 `-Xmx2g` 可支撑 500 万行全量；若单批 > 2000 万行或并发多个迁移，调到 `-Xmx4g`（机器内存 ≥ 8G）。
- **batchSize**：跨库/文件导入建议 2000～5000；太大增加单语句解析开销，太小增加往返。
- **增量优先**：`mode=INCREMENTAL` + 水位字段，每批推进水位，失败可续传/回滚；比一次性全量更稳。
- **避开高峰**：迁移会占用磁盘 IO 与网络，建议业务低峰执行；同库迁移是数据库内部 `INSERT…SELECT`，对应用侧内存几乎无压力。
- **网络**：跨网络（经 SOCKS5/HTTP 代理）时带宽是首要瓶颈；可先 `mysqldump` 压缩后走 FTP 摆渡，再在目标端导入。
- **索引**：目标表在导入期间可先删除二级索引，导入完成后再建，通常可再快 1.5～3 倍。

## 6. 复跑方法

```bash
# 在测试机执行（默认 100 万行，可用 ROWS 覆盖）
sudo bash deploy/cmds/lan_bench_migration.sh
# 500 万行
sudo sed 's/1000000/5000000/' deploy/cmds/lan_bench_migration.sh > /tmp/bench5m.sh && sudo bash /tmp/bench5m.sh
```

脚本会：建表造数 → 同库迁移 → 跨库迁移 → FTP 导出/导入，并每 1s 采样 JVM RSS，最后清理测试表与项目。
