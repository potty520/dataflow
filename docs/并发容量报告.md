# DGP 平台并发容量报告（优化前后对比）

> 环境：`<server-ip>`，**1 vCPU / 2GB**（与另外 4 个 Java 服务共用），MySQL 8.0.46 同机
> 入口：`http://<server-ip>:8093`（nginx，推荐）/ `http://<server-ip>:8092`（直连后端）
> 压测方式：服务器本机 `wrk -t2 -d15s`（排除公网 RTT，只测服务端能力），登录用 `ab`（POST JSON）
> 时间：2026-10-21

## 1. 结论

| 指标 | 优化前 | 优化后（c=200） | 提升 |
|---|---|---|---|
| 治理概览看板 `/overview/dashboard` | **17 QPS** | **2324 QPS**（直连）/ 1754 QPS（经 nginx） | **≈137 倍** |
| 元数据列表 `/metadata/tables` | 212 QPS（c=100） | 307 QPS | 1.45 倍 |
| 服务列表 `/service/apis` | 351 QPS | 551 QPS | 1.57 倍 |
| 质量列表 `/quality/checks` | 108 QPS | 142 QPS | 1.3 倍 |
| 前端主 JS（1.3MB） | **45 QPS** | **2804 QPS**（nginx + gzip_static） | **≈64 倍** |
| 首页 index.html | — | 8361 QPS | — |
| 登录（PBKDF2 210k） | 2.4 次/秒 | 2.8 次/秒 | CPU 受限，未降安全强度 |

**结论：单机 1 核在优化后可支撑「约 100~200 并发用户」的混合读场景（看板类 p95 < 500ms、页面秒开）；若目标 500~1000 并发，需要升配到 4 vCPU/8GB 或多实例 + nginx 分流。**

## 2. 瓶颈定位（基线压测）

基线在并发 10 时：概览看板 p50 115ms、仅 16.6 QPS；并发 100 时出现 193 次 2s 超时。原因有三：

1. **概览看板单请求 30 条 SQL**（KPI 14 条 + 趋势/分组/最近记录 16 条），1 核上每条几毫秒，串行 100~250ms；
2. **每个已登录请求额外 3 次鉴权查询**：`sys_token_blacklist` + `sys_user` + `sys_role.perms`；
3. **静态资源由 Tomcat 直接输出**：1.3MB JS 每次 45 QPS，压缩与 sendfile 都没用上。

## 3. 已实施的优化

### 3.1 代码层

| 改动 | 说明 | 效果 |
|---|---|---|
| `TtlCache` 进程内缓存 | 概览看板 15s、元数据/安全统计 15s、资产 20s、服务 10s、质量 8~10s；写操作统一 `TtlCache.clear()` 保证"改完立刻可见" | 看板 17→2324 QPS |
| 鉴权结果缓存 | 用户 30s / 权限 60s / 登出黑名单内存化（10s 与库对齐，支持多实例）；用户与权限变更接口即时失效 | 读请求鉴权查询 3 次 → **0 次** |
| 保留 PBKDF2 210k | 未降低口令安全强度；登录属一次性高成本操作 | 2.8 次/秒（1 核） |

### 3.2 运行时配置

- Tomcat：`threads.max=400`、`accept-count=1000`、`max-connections=10000`、`keep-alive-timeout=60s`、`connection-timeout=30s`
- Hikari（MySQL）：`maximum-pool-size=24`、`minimum-idle=4`（配合鉴权缓存，单请求 0~5 条 SQL 足够）
- 连接初始化：`PIPES_AS_CONCAT`、`max_execution_time=60000`、`innodb_lock_wait_timeout=10`

### 3.3 nginx 反向代理（新增 8093 端口，不影响服务器已有站点）

- 静态资源：`sendfile` 直出 + **部署时预生成 `.gz`**（`gzip_static on`，运行时零压缩 CPU）+ `/assets/*` `Cache-Control: public, immutable`（一年强缓存）
- API：`/api/`、`/open/` 反代 8092，保持 upstream keepalive；**不压缩代理响应**（1 核上实时 gzip 反而降低并发）
- `chunked_transfer_encoding off`：与后端 `ContentLengthFilter` 双保险，规避公网中间设备对分块响应的错误处理（浏览器 `ERR_INVALID_CHUNKED_ENCODING`）
- 同源部署剥离 `Origin`，避免 CORS 白名单与代理端口不一致
- 部署脚本 `deploy/remote.py` 每次发版自动同步静态资源、重载 nginx

## 5. 容量结论与扩容建议

| 目标并发用户 | 建议配置 | 说明 |
|---|---|---|
| ≤ 200 | 当前 1 vCPU / 2GB 可用 | 看板/列表 p95 < 500ms，静态秒开 |
| 500 ~ 1000 | 4 vCPU / 8GB，MySQL 单独 512MB~1G buffer pool | CPU 是唯一硬瓶颈；核数≈线性提升 |
| 1000+ | 2 台 + 2 vCPU 应用 + nginx 轮询 | 应用无状态（JWT），可直接水平扩展 |

- **登录突发**：1 核约 2.8 次/秒；演示/内网场景足够，若公网开放建议登录页限流或独立认证服务，不建议降低 PBKDF2 迭代数。
- **MySQL 调优**（升配后）：`innodb_buffer_pool_size` 128MB→1GB、`max_connections` 151→300、`innodb_flush_log_at_trx_commit=2`（可接受 1s 事务丢失时提升写吞吐）。
- **水平扩展注意**：本地 TTL 缓存有 8~20s 级最终一致（可接受）；登出黑名单 10s 内跨实例对齐；JWT 密钥需一致（`DGP_JWT_SECRET`）。
